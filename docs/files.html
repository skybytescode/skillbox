🗂️ Sisteme de fișiere

Ghid complet și detaliat despre organizarea fișierelor, structura de directoare, sistemele de fișiere native, permisiuni și particularități pe Linux, Windows, macOS, Android și iOS.

Cuprins

    1Ce este un sistem de fișiere?

    Un sistem de fișiere (filesystem) este structura de date și setul de reguli prin care un sistem de operare organizează, denumește, stochează și regăsește informația pe un suport de stocare (SSD, HDD, card SD, memorie flash). El răspunde la trei întrebări fundamentale: unde este stocat fiecare bloc de date, cum se numesc și se organizează fișierele/directoarele, și cine are voie să le acceseze.

    Fișier

    O secvență de octeți cu un nume, stocată ca unitate. Are conținut (datele propriu-zise) și metadate (dimensiune, dată, proprietar, permisiuni).

    Director / folder

    Un fișier special care conține o listă de intrări (nume → alt fișier sau director), formând o structură arborescentă (ierarhică).

    Cale (path)

    Adresa unui fișier în arbore: absolută (de la rădăcină) sau relativă (de la directorul curent).

    Metadate

    Informații despre fișier, separate de conținut: dimensiune, timestamp-uri, proprietar, permisiuni, atribute (ascuns, doar-citire etc).

    Inode / MFT record

    Structura internă care leagă un nume de fișier de locația reală a datelor pe disc (inode pe Unix/Linux, MFT record pe NTFS).

    Jurnalizare (journaling)

    Tehnică prin care sistemul de fișiere scrie mai întâi într-un jurnal ce urmează să facă, pentru a se putea recupera după o cădere bruscă de curent.

    Deși principiile sunt universale, fiecare familie de sisteme de operare a dezvoltat propriile convenții de organizare și propriile sisteme de fișiere native, optimizate pentru cazul ei de utilizare. Sări direct la un capitol:

    🐧Linux 🪟Windows 🍎macOS 🤖Android 📱iOS

    2Linux — structura ierarhică de fișiere

    Linux (ca orice Unix) folosește un singur arbore de directoare, cu rădăcina notată /. Nu există litere de unitate ca în Windows — discuri, partiții, USB-uri sau chiar sisteme de fișiere de rețea sunt toate montate (mount) ca subdirectoare în acest arbore unic. Organizarea directoarelor standard este definită de FHS — Filesystem Hierarchy Standard.

    /
├── bin, sbin      → executabile esențiale (azi, de regulă link către /usr/bin)
├── boot           → kernel (vmlinuz), initramfs, GRUB
├── dev            → fișiere de dispozitiv (/dev/sda, /dev/null, /dev/tty)
├── etc            → fișiere de configurare la nivel de sistem
├── home           → directoarele personale ale utilizatorilor (/home/ana)
├── lib, lib64     → biblioteci partajate necesare pentru /bin și /sbin
├── media, mnt     → puncte de montare pentru medii amovibile / temporare
├── opt            → software opțional, terță parte, autonom
├── proc           → pseudo-sistem de fișiere: informații live despre procese/kernel
├── root           → directorul personal al utilizatorului root
├── run            → date volatile de runtime (PID-uri, socket-uri), pierdute la reboot
├── srv            → date pentru servicii găzduite pe mașină (ex: site-uri web)
├── sys            → pseudo-sistem de fișiere: informații despre kernel/hardware
├── tmp            → fișiere temporare, șterse de obicei la reboot
├── usr            → programe, biblioteci, documentație "userland" (partea cea mai mare)
└── var            → date variabile: loguri (/var/log), cache, cozi de mail, baze de date
    💡 /proc și /sys nu ocupă spațiu real pe disc — sunt "ferestre" virtuale generate de kernel la citire, folosite pentru introspecție (cat /proc/cpuinfo, cat /proc/meminfo).

    Sisteme de fișiere native

    Sistem de fișiereCaracteristici
    ext4Implicit pe majoritatea distribuțiilor (Ubuntu, Debian). Jurnalizat, matur, stabil, suportă volume de până la 1 EiB.
    BtrfsCopy-on-write, snapshot-uri native, subvolume, compresie transparentă, RAID software integrat. Implicit pe openSUSE și Fedora Workstation (parțial).
    XFSFoarte performant pe fișiere mari și paralelism ridicat; implicit pe RHEL/CentOS.
    ZFSCombină filesystem + volume manager: snapshot-uri, deduplicare, checksum-uri end-to-end. Popular pe servere de storage (adesea prin OpenZFS).
    F2FSOptimizat pentru memorie flash (SSD/eMMC) — folosit pe unele dispozitive Android.

    Permisiuni: model rwx (owner / group / others)

    Fiecare fișier are un proprietar, un grup și permisiuni separate pentru trei categorii de utilizatori: proprietar (u), grup (g) și restul (o). Pentru fiecare categorie există trei drepturi: read, write, execute.

    rwx r-x r-- = rwxr-xr-- = 754 (owner: citește/scrie/execută, grup: citește/execută, alții: doar citește) 
    chmod 755 script.sh      # rwxr-xr-x, numeric
chmod u+x script.sh       # adaugă execuție doar proprietarului, simbolic
chown ana:staff fisier    # schimbă proprietarul și grupul
chmod +t /tmp             # sticky bit: doar proprietarul poate șterge fișierul din director
    🔐 Pe un director, x înseamnă "poți intra/traversa" (cd), nu "poți executa". Fără x pe director, nu poți accesa fișierele din el chiar dacă ai r.

    Legături, fișiere ascunse și puncte de montare

    • Hard link (ln) — un al doilea nume pentru același inode; fișierul dispare fizic doar când ultimul nume care îl referă este șters.
    • Symlink (ln -s) — un fișier special ce conține o cale către alt fișier; se poate rupe dacă ținta e mutată/ștearsă.
    • Fișiere ascunse — orice nume care începe cu punct (.bashrc, .config); nu e un atribut separat, e doar convenție, ascunsă de ls fără -a.
    • Mount points — un disc nou nu apare ca literă separată, ci "grefat" într-un director existent (mount /dev/sdb1 /mnt/date).

    3Windows — litere de unitate și NTFS

    Windows folosește un model cu litere de unitate (C:, D:...): fiecare partiție sau disc are propriul arbore de directoare, nu există o rădăcină unică pentru tot sistemul. Separatorul de cale este backslash-ul \ (deși API-urile moderne acceptă și /).

    C:\
├── Windows                → sistemul de operare propriu-zis
│   └── System32           → executabile și DLL-uri critice de sistem
├── Program Files           → aplicații pe 64 de biți
├── Program Files (x86)     → aplicații pe 32 de biți (compatibilitate)
├── ProgramData              → date partajate ale aplicațiilor, ascuns implicit
├── Users
│   └── NumeUtilizator
│       ├── Desktop, Documents, Downloads, Pictures...
│       └── AppData
│           ├── Local       → date locale mașinii, nu se sincronizează
│           ├── LocalLow    → date cu nivel scăzut de integritate (ex: sandbox browser)
│           └── Roaming     → date care urmăresc profilul, se pot sincroniza în rețea
└── System Volume Information → date interne de restaurare a sistemului

    Sisteme de fișiere native

    Sistem de fișiereCaracteristici
    NTFSImplicit pentru discul de sistem. Jurnalizat, suportă permisiuni ACL detaliate, compresie, criptare (EFS), cote de disc, fișiere de până la 16 TB, nume până la 255 caractere.
    exFATFără jurnalizare, fără permisiuni complexe; folosit pe stick-uri USB și carduri SD pentru compatibilitate cross-platform (Windows/macOS/Linux/camere/console).
    FAT32Vechi, dar universal compatibil; limitat la fișiere de max. 4 GB și volume de 32 GB (formatare nativă Windows).
    ReFS"Resilient File System" — mai nou, orientat spre integritate a datelor (checksum-uri automate); folosit mai ales pe Windows Server și Storage Spaces.

    Permisiuni: ACL, nu doar rwx

    NTFS folosește liste de control al accesului (ACL): fiecare fișier poate avea reguli separate pentru oricâți utilizatori sau grupuri, nu doar trei categorii ca pe Unix. Drepturile includ Read, Write, Modify, Read & Execute, List folder contents, Full control — și pot fi Allow sau Deny explicit.

    icacls fisier.txt /grant Ana:(R,W)      # acordă citire/scriere userului Ana
icacls fisier.txt /remove Ana           # elimină regula
attrib +h +s fisier.txt                 # marchează fișier ca ascuns + sistem
dir /a                                  # listează inclusiv fișierele ascunse
    💡 Spre deosebire de Linux, pe Windows "fișier ascuns" este un atribut real stocat în metadate (Hidden), setat cu attrib +h, nu doar o convenție de denumire.

    Legături pe NTFS

    • Shortcut (.lnk) — fișier obișnuit interpretat de Explorer, nu o legătură reală la nivel de filesystem.
    • Symbolic link (mklink) — echivalentul symlink-ului Unix, disponibil din Windows Vista încoace.
    • Junction (mklink /J) — leagă un director de altul, dar funcționează doar local, pe același volum sau computer.

    4macOS — un Unix cu pachete de aplicații

    macOS este construit pe Darwin, un nucleu de tip Unix (XNU) — de aceea structura de bază seamănă cu Linux: un singur arbore, rădăcină /, permisiuni POSIX rwx. Discurile suplimentare apar montate în /Volumes, nu ca litere separate.

    /
├── Applications      → aplicații instalate pentru toți utilizatorii (.app bundles)
├── System            → fișierele sistemului de operare (protejate, read-only de SIP)
│   └── Volumes/Data  → pe macOS modern, datele scriptibile sunt pe un volum separat
├── Library           → preferințe, cache, plugin-uri partajate la nivel de sistem
├── Users
│   └── NumeUtilizator
│       ├── Desktop, Documents, Downloads, Movies, Pictures...
│       └── Library    → preferințe și date specifice userului (ascuns implicit)
├── Volumes           → puncte de montare pentru discuri externe/imagini
└── private/etc, /private/var → configurări și date variabile (linkuri: /etc → /private/etc)

    Sisteme de fișiere native

    Sistem de fișiereCaracteristici
    APFS (Apple File System)Implicit din 2017 pe SSD/Mac moderne. Copy-on-write, snapshot-uri instant, criptare nativă per-volum, clonare instantanee de fișiere, spațiu partajat între "volume container".
    HFS+Sistemul de fișiere clasic Mac, precursor al APFS; încă întâlnit pe discuri mai vechi sau medii de recuperare.

    Pachete .app și atribute extinse

    O aplicație macOS (Safari.app) nu e un singur executabil, ci un director "pachet" (bundle) care conține binarul, resursele, iconițele și metadatele — Finder îl afișează ca un singur fișier, dar ls în terminal arată structura reală (Contents/MacOS, Contents/Resources, Info.plist).

    macOS folosește pe scară largă atributele extinse (xattrs) — metadate suplimentare atașate oricărui fișier, invizibile în majoritatea uneltelor: tag-uri Finder, comentarii, sau flag-ul com.apple.quarantine pus pe fișierele descărcate din internet (motiv pentru avertismentul Gatekeeper la prima rulare).

    chmod 644 fisier.txt        # POSIX rwx, la fel ca pe Linux
xattr -l fisier.txt         # listează atributele extinse
xattr -d com.apple.quarantine fisier.txt   # scoate carantina descărcărilor
ls -la ~/                   # arată și fișierele ascunse (.bash_profile, .ssh...)
    🔒 System Integrity Protection (SIP) face /System read-only chiar și pentru root, prevenind modificarea fișierelor critice de malware sau greșeli ale utilizatorului.

    5Android — Linux cu sandbox pe fiecare aplicație

    Android rulează pe un kernel Linux real, deci moștenește permisiunile POSIX și un arbore unic de directoare — dar adaugă un strat puternic de izolare: fiecare aplicație rulează cu propriul UID Linux unic, ceea ce o transformă practic într-un "utilizator" separat pentru sistemul de fișiere.

    /
├── system            → SO-ul Android propriu-zis, read-only (partiție /system)
├── data
│   ├── data/com.app.exemplu   → sandbox privat al fiecărei aplicații (owner = UID-ul ei)
│   └── ...
├── sdcard → storage/emulated/0   → stocarea "partajată", vizibilă în Files/Galerie
│   ├── DCIM, Download, Pictures, Android/data/...
├── vendor            → drivere și blob-uri specifice producătorului de hardware
└── proc, sys, dev    → identice conceptual cu Linux desktop

    Scoped storage și sandboxing

    • Sandbox privat (/data/data/<pachet>) — accesibil doar aplicației proprietare (și root, pe dispozitive rootate); alte aplicații nu pot citi datele fără permisiune explicită.
    • Scoped storage (Android 10+) — aplicațiile nu mai văd liber tot stocajul partajat; trebuie să ceară acces prin API-uri de sistem (Storage Access Framework) sau se limitează la propriul director Android/data/<pachet>.
    • Permisiuni runtime — accesul la stocarea partajată (fotografii, fișiere) e cerut explicit userului la runtime, nu doar declarat static în manifest.

    Sisteme de fișiere

    Sistem de fișiereUtilizare
    ext4Cel mai comun pentru partiția /data pe dispozitive mai vechi.
    F2FSOptimizat pentru memorie flash NAND, tot mai des implicit pe telefoane moderne.
    exFAT / FAT32Pe carduri microSD amovibile, pentru compatibilitate cu alte dispozitive/PC.
    💡 Fără root, nu poți naviga în /data/data/altapp nici măcar cu un file manager — sandboxing-ul e impus de kernel prin UID-uri, exact ca separarea dintre utilizatori pe Linux desktop.

    6iOS / iPadOS — fără sistem de fișiere vizibil global

    iOS rulează tot pe Darwin/XNU și pe APFS, la fel ca macOS, dar filosofia e radical diferită: nu există, în mod normal, acces la un arbore global de fișiere. Fiecare aplicație trăiește într-un container sandbox propriu, complet izolat de containerele celorlalte aplicații.

    /var/containers/Bundle/Application/<UUID>/AppExemplu.app   → codul aplicației (read-only)
/var/mobile/Containers/Data/Application/<UUID>/
├── Documents/     → date create de user, incluse în backup
├── Library/
│   ├── Preferences/   → UserDefaults / setări
│   └── Caches/        → date temporare, NU incluse în backup
└── tmp/                → șterse periodic de sistem

    Cum interacționează utilizatorul cu fișierele

    • Aplicația Files — oferă o vedere unificată peste "On My iPhone/iPad" (stocarea locală expusă intenționat de aplicații) + iCloud Drive + furnizori terți (Google Drive, Dropbox) prin Document Provider API.
    • Fără Finder/Explorer clasic — nu poți naviga liber în containerul altei aplicații sau în fișierele de sistem, nici măcar ca proprietar al dispozitivului, fără jailbreak.
    • iCloud Drive — sincronizare la nivel de fișier, cu descărcare "la cerere" (fișierele pot exista doar ca metadate locale, cu conținutul păstrat în cloud până la accesare).
    • App Groups — singura excepție de partajare: aplicații ale aceluiași dezvoltator pot partaja explicit un container comun (ex: aplicația principală și widget-ul ei).
    🔐 Această izolare extremă e motivul pentru care iOS are un istoric de malware mult mai redus decât desktop-urile tradiționale — o aplicație compromisă nu poate, în mod normal, citi datele alteia.

    8Glosar de concepte comune

    Symlink

    Fișier care conține doar o cale către alt fișier/director; se poate "rupe" dacă ținta dispare. Disponibil pe toate cele 5 sisteme.

    Hard link

    Al doilea nume pentru exact aceleași date pe disc (același inode/MFT record). Nu există pentru directoare pe majoritatea sistemelor.

    Inode / MFT

    Structura care ține metadatele unui fișier separat de numele lui — de aceea poți redenumi un fișier fără să-i muți conținutul.

    Jurnalizare

    Scriere prealabilă într-un jurnal a operațiilor planificate, pentru recuperare rapidă și consistentă după o cădere de curent (ext4, NTFS, APFS, HFS+ toate jurnalizează).

    Copy-on-write (CoW)

    La modificare, se scrie un bloc nou în loc să se suprascrie cel vechi — stă la baza snapshot-urilor instant (Btrfs, ZFS, APFS).

    Extensie de fișier

    Sufixul după ultimul punct (.txt, .app) — convenție pentru a asocia tipul de conținut cu o aplicație; Linux nu se bazează pe ea (folosește magic bytes), Windows/macOS/iOS/Android o folosesc frecvent, dar nu exclusiv.

    Sandbox / container

    Izolarea unei aplicații într-un spațiu propriu de fișiere, cu acces restricționat în afara lui — model central pe Android și iOS, opțional pe desktop (Flatpak, Snap, App Sandbox macOS).

    Mount / montare

    Procesul prin care un sistem de fișiere (disc, partiție, imagine, share de rețea) devine vizibil într-un punct din arborele de directoare.
