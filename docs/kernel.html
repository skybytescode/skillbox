Cuprins

    1Ce este kernel-ul?

    Kernel-ul (nucleul) este programul central al unui sistem de operare: singurul cod care rulează cu acces total la hardware. El este intermediarul obligatoriu între aplicațiile pe care le rulezi și procesor, memorie, discuri, plăci de rețea și restul dispozitivelor fizice.

    Linux desemnează strict acest nucleu — creat de Linus Torvalds în 1991, ca proiect personal inspirat de Unix și Minix. Ce numim colocvial "Linux" (Ubuntu, Fedora, Debian etc.) este de fapt o distribuție: nucleul Linux + unelte GNU + un manager de pachete + software userland, ambalate împreună.

    Aplicații (bash, firefox, nginx, python...)
    ↕ apeluri de bibliotecă
    Biblioteci (glibc, libc...)
    ↕ apeluri de sistem (syscalls)
    KERNEL LINUXscheduler · memorie · VFS · rețea · drivere · IPC
    ↕ instrucțiuni + întreruperi
    HardwareCPU · RAM · disc · placă de rețea · GPU...

    Kernel-ul e singurul strat care "atinge" hardware-ul direct. Totul deasupra lui trece prin el.

    Kernel vs. sistem de operare vs. distribuție

    TermenCe înseamnă
    KernelCodul care gestionează procesoare, memorie, dispozitive și oferă serviciile de bază (fișiere, procese, rețea) restului sistemului.
    Sistem de operareKernel + toate uneltele minime necesare să faci ceva util cu el (shell, comenzi, biblioteci).
    Distribuție (distro)Un SO complet, "la pachet": kernel + userland GNU + manager de pachete + configurări implicite + suport (ex: Ubuntu, Debian, Fedora, Arch).
    💡 Toate distribuțiile Linux (Ubuntu, Fedora, Arch, Alpine, Android...) folosesc, în esență, același kernel Linux (eventual cu patch-uri), dar diferă complet în userland, unelte de instalare și filosofie.

    2Rolurile fundamentale ale kernel-ului

    Indiferent de arhitectură, orice kernel modern trebuie să rezolve aceleași patru probleme:

    1. Management procese

    Decide ce proces rulează, când, pe care nucleu CPU, și pentru cât timp (scheduling). Izolează procesele unele de altele.

    2. Management memorie

    Alocă și protejează memoria RAM pentru fiecare proces, folosind memorie virtuală, astfel încât un proces să nu poată citi memoria altuia.

    3. Acces la dispozitive

    Oferă o interfață uniformă (fișiere, drivere) peste hardware eterogen: discuri, plăci de rețea, USB, GPU etc.

    4. Comunicare & fișiere

    Implementează sistemele de fișiere, rețeaua (stiva TCP/IP) și mecanismele prin care procesele comunică între ele (IPC).

    Toate aceste servicii sunt expuse programelor din userspace printr-un set fix de funcții numite apeluri de sistem (system calls) — vezi secțiunea 4.

    3Tipuri de arhitecturi de kernel

    Modul în care un kernel își organizează intern subsistemele definește trei mari familii de arhitecturi:

    Monolitic

    Drivere
    Sistem fișiere
    Rețea
    Scheduler
    Aplicație

    Tot (drivere, VFS, rețea, scheduler) rulează în același spațiu privilegiat (kernel space). Rapid — apeluri de funcție directe — dar un bug într-un driver poate pica tot sistemul. Linux e monolitic (dar modular, vezi mai jos).

    Microkernel

    IPC minim + scheduler
    Driver disc (proces)
    Sistem fișiere (proces)
    Aplicație

    Doar strictul necesar (IPC, scheduler de bază) rulează privilegiat; drivere și sisteme de fișiere rulează ca procese userspace separate, comunicând prin mesaje. Mai robust la crash-uri, dar mai lent (multe treceri kernel↔user). Ex: Minix, QNX, seL4.

    Hibrid

    Nucleu de bază + drivere critice
    Servicii încărcate dinamic
    Aplicație

    Combină ideile: nucleu compact + module/servicii care pot rula privilegiat sau nu, după caz. Ex: Windows NT, macOS (XNU).

    🧩 Linux este monolitic, dar modular: toate subsistemele rulează în kernel space (ca într-un monolitic clasic), însă multe componente (drivere, sisteme de fișiere, protocoale) pot fi compilate ca module încărcabile (.ko) și adăugate/scoase din kernel-ul care rulează, fără repornire — vezi secțiunea 8. Practic ia din viteza monoliticului și din flexibilitatea microkernel-ului.

    4Kernel space, user space și apelurile de sistem

    CPU-urile moderne au niveluri de privilegiu ("ring"-uri). Linux folosește practic doar două: kernel space (ring 0 — acces total la hardware) și user space (ring 3 — acces restricționat, sandbox-at de kernel). Această separare e ceea ce previne ca o aplicație obișnuită să corupă memoria altui proces sau a kernel-ului.

    Când o aplicație are nevoie de un serviciu al kernel-ului (să deschidă un fișier, să aloce memorie, să creeze un proces), nu poate accesa direct hardware-ul — face un apel de sistem (system call):

    1. Aplicație
    apelează read() din libc
    →
    2. glibc
    pregătește registrele, execută instrucțiunea syscall/int 0x80
    →
    3. Trap → kernel
    CPU trece din ring 3 în ring 0
    →
    4. Handler kernel
    execută codul real (ex: citește de pe disc)
    →
    5. Return
    rezultatul e copiat înapoi, CPU revine în ring 3

    Linux expune câteva sute de apeluri de sistem (vezi man syscalls) — open, read, write, close, fork, execve, mmap, socket, ioctl etc. Ele formează ABI-ul stabil al kernel-ului: interfața pe care Linux se angajează să nu o "rupă" niciodată pentru programele existente.

    $ strace -c ls          # numără fiecare syscall folosit de comanda ls
$ strace -e trace=open,read cat /etc/hostname   # urmărește syscall-uri specifice
    🔐 Capabilities rafinează modelul "root vs. restul": în loc de tot-sau-nimic, un proces poate primi doar privilegii punctuale (ex. CAP_NET_BIND_SERVICE pentru a asculta pe portul 80 fără a fi root complet). Vezi man capabilities.

    5Harta subsistemelor kernel-ului Linux

    Codul sursă al kernel-ului Linux (peste 30 de milioane de linii, în kernel.org) e organizat pe subsisteme mari, fiecare cu propriul mentor/maintainer:

    Process Scheduler

    Decide ce fir de execuție rulează pe fiecare nucleu CPU și când (CFS, EEVDF, real-time). Secțiunea 6.

    Memory Management (mm)

    Memorie virtuală, paginare, alocatoare (buddy, slab/slub), swap, OOM killer. Secțiunea 7.

    VFS & Filesystems

    Stratul unificat de fișiere peste ext4, btrfs, XFS, NFS, procfs, sysfs... Secțiunea 8.

    Device Drivers

    Cea mai mare parte a codului sursă: drivere pentru discuri, plăci video, USB, senzori etc. Secțiunea 9.

    Networking

    Stiva completă TCP/IP, netfilter (firewall), socket API. Secțiunea 10.

    IPC & sincronizare

    Pipe-uri, semnale, semafoare, memorie partajată, spinlocks, mutexes, RCU. Secțiunea 11.

    Namespaces & cgroups

    Izolare și limitare de resurse — fundația containerelor (Docker, Kubernetes). Secțiunea 12.

    Security (LSM)

    SELinux, AppArmor, seccomp — restricții suplimentare peste modelul clasic user/root. Secțiunea 13.

    Arch-specific code

    Cod specific fiecărei arhitecturi de CPU: x86_64, ARM64, RISC-V etc. (arch/ în sursă).

    6Managementul proceselor și schedulerul

    Pentru kernel, un proces e descris de o structură task_struct (PID, memorie, fișiere deschise, stare, prioritate...). Un proces poate avea mai multe fire de execuție (threads), care partajează memoria dar au propriul stivă și registre.

    Stările unui proces

    Created
    fork()/clone()
    →
    Ready
    așteaptă rândul la CPU
    →
    Running
    execută pe un nucleu CPU
    →
    Waiting/Sleeping
    așteaptă I/O sau un eveniment
    →
    Terminated/Zombie
    a ieșit, așteaptă ca părintele să facă wait()

    Running ↔ Ready se repetă continuu (schimbare de context); Waiting revine în Ready când evenimentul așteptat sosește.

    Schedulere disponibile în Linux

    SchedulerPentruIdee de bază
    CFS (Completely Fair Scheduler)procese normalefiecare proces primește o "cotă echitabilă" de timp CPU proporțională cu nice; folosește un red-black tree ordonat după "vruntime".
    EEVDF (din kernel 6.6+)procese normalesuccesorul CFS — planifică pe baza unui "termen limită virtual" pentru latență mai bună.
    SCHED_FIFO / SCHED_RRtimp real (soft/hard)prioritate fixă, rulează până cedează CPU singur (FIFO) sau la cuantă fixă (Round-Robin); au mereu prioritate peste CFS.
    SCHED_DEADLINEtimp real cu deadlineEarliest Deadline First — pentru sarcini cu constrângeri stricte de timp.

    Prioritatea "clasică" a unui proces normal se ajustează cu nice, între -20 (cea mai mare prioritate) și +19 (cea mai mică):

    $ nice -n 10 ./script.sh      # pornește cu prioritate mai mică
$ renice -n -5 -p 1234        # schimbă prioritatea unui proces existent (necesită root pentru valori negative)
$ chrt -f 50 ./realtime_app    # rulează cu SCHED_FIFO, prioritate 50
    ⚙️ Context switch = operația prin care CPU salvează starea procesului curent și încarcă starea altuia. E rapid, dar nu gratuit — de aceea sistemele cu mii de thread-uri active pot deveni mai lente doar din cauza switch-urilor dese ("thrashing").

    7Managementul memoriei

    Fiecare proces "vede" propriul spațiu de adrese virtual și izolat, de obicei 128 TiB pe 64-bit — chiar dacă mașina are mult mai puțină memorie RAM fizică. Kernel-ul (prin MMU-ul procesorului) traduce adresele virtuale în adrese fizice folosind tabele de pagini.

    Kernel space (partajat, protejat)
    Stivă (stack) ↓ crește în jos
    Memory-mapped regionbiblioteci .so, mmap()
    Heap ↑ crește în sus (malloc)
    BSSvariabile globale neinițializate
    Datavariabile globale inițializate
    Textcodul executabil

    Spațiul virtual de adrese al unui proces pe 64-bit (simplificat)

    Concepte cheie

    • Paginare (paging) — memoria e împărțită în pagini (de obicei 4 KiB); tabelele de pagini mapează pagini virtuale → cadre fizice.
    • TLB — un cache hardware pentru traducerile de adrese recente, ca MMU-ul să nu parcurgă tabelele de pagini la fiecare acces.
    • Copy-on-write (COW) — după fork(), părinte și copil partajează aceleași pagini fizice până când unul dintre ei scrie; abia atunci se copiază pagina.
    • Swap — pagini rar folosite sunt mutate pe disc quando RAM-ul e insuficient, eliberând spațiu fizic.
    • Alocatoare interne — buddy allocator pentru pagini întregi, slab/slub allocator pentru obiecte mici, frecvent (re)alocate din kernel (ex: task_struct).
    • OOM killer — când memoria (RAM+swap) se epuizează complet, kernel-ul alege și termină forțat un proces ("oom-score" mai mare = țintă mai probabilă) ca să salveze sistemul.
    $ free -h                  # memorie liberă/folosită/swap
$ cat /proc/meminfo         # detalii complete despre memorie
$ cat /proc/<pid>/status | grep Vm   # memoria unui proces specific
$ vmstat 1                  # statistici memorie/CPU live

    8Sistemul de fișiere virtual (VFS) și modulele de kernel

    VFS (Virtual File System) e un strat de abstractizare: oferă aceleași apeluri (open, read, write, stat...) indiferent dacă fișierul e pe ext4, pe o cheie USB cu FAT32, pe un server NFS, sau reprezintă o structură din kernel (procfs).

    Sistem de fișiereTipObservații
    ext4disc, jurnalizatimplicit pe majoritatea distribuțiilor, matur și stabil.
    btrfsdisc, copy-on-writesnapshot-uri, subvolume, checksum-uri; implicit pe openSUSE/Fedora Workstation.
    xfsdisc, jurnalizatperformant pe fișiere mari; implicit pe RHEL.
    procfs (/proc)virtualexpune starea proceselor și a kernel-ului ca "fișiere" (nu ocupă disc).
    sysfs (/sys)virtualexpune dispozitivele și parametrii kernel-ului (folosit de udev).
    tmpfsvirtual, RAMmontat des pe /tmp sau /dev/shm: rapid, dispare la reboot.
    NFS/CIFSrețeamontează sisteme de fișiere expuse de alte mașini.

    Module de kernel (LKM — Loadable Kernel Modules)

    Un modul (fișier .ko) e cod ce poate fi injectat sau scos din kernel-ul care rulează, fără repornire — de obicei drivere sau sisteme de fișiere folosite ocazional.

    $ lsmod                        # module curent încărcate
$ modprobe nvidia               # încarcă un modul (+ dependențele lui)
$ modprobe -r nvidia             # descarcă modulul
$ modinfo e1000e                # informații despre un modul (autor, parametri, licență)
$ dmesg | tail                  # log-ul kernel-ului — util imediat după (de)încărcarea unui modul
    📂 "Totul e un fișier" se aplică și dispozitivelor: /dev/sda (disc), /dev/tty1 (terminal), /dev/null — toate sunt "fișiere speciale" prin care userspace vorbește cu drivere din kernel, folosind aceleași read()/write()/ioctl().

    9Întreruperi (interrupts) și I/O

    Hardware-ul nu așteaptă politicos să fie interogat — anunță kernel-ul cu o întrerupere hardware (IRQ) (ex: a sosit un pachet de rețea, tastatura a fost apăsată, discul a terminat un transfer DMA). Kernel-ul oprește orice face și rulează un handler de întrerupere.

    Hardware IRQ
    placă de rețea/disc semnalează un eveniment
    →
    Top half
    handler minimal, foarte rapid, întreruperi dezactivate
    →
    Bottom half
    softirq / tasklet / workqueue — restul procesării, amânat
    →
    Userspace
    procesul așteptat e trezit (ex: read() revine)

    Această separare top half / bottom half există ca handler-ele de întrerupere să fie cât mai scurte (rulează cu întreruperile dezactivate) — restul muncii se amână pentru mai târziu, când sistemul poate din nou răspunde la alte întreruperi.

    • DMA (Direct Memory Access) — permite dispozitivelor să transfere date direct în/din RAM fără să ocupe CPU-ul pentru fiecare octet.
    • Polling vs. interrupt-driven — pentru dispozitive foarte rapide (rețea 10G+), Linux poate comuta temporar pe polling (NAPI) ca să evite "furtuni" de întreruperi.
    $ cat /proc/interrupts     # câte întreruperi de fiecare tip a servit fiecare CPU

    10Stiva de rețea

    Kernel-ul Linux implementează complet stiva TCP/IP, de la driverul plăcii de rețea până la API-ul de socket-uri folosit de aplicații.

    Aplicație (socket API: socket(), send(), recv())
    Transport: TCP / UDP
    Rețea: IP, routing, netfilter (firewall)
    Legătură de date: Ethernet, ARP
    Driver placă de rețea (NIC)
    • netfilter — framework-ul din kernel pe care se bazează iptables/nftables (firewall, NAT, port forwarding).
    • Network namespaces — fiecare namespace are propria stivă de rețea izolată (interfețe, rute, reguli firewall) — cum funcționează rețeaua în containere.
    • eBPF — permite injectarea de mici programe verificate direct în kernel (rețea, tracing, securitate) fără a scrie module — folosit de unelte precum Cilium sau Falco.
    $ ss -tulpn                 # socket-uri deschise (TCP/UDP, listen)
$ ip route                  # tabela de rutare a kernel-ului
$ iptables -L -n            # regulile de firewall active

    11IPC și sincronizare în kernel

    Comunicare între procese (IPC)

    MecanismFolosit pentru
    Pipe / FIFOflux de octeți unidirecțional între procese înrudite (cmd1 | cmd2).
    Semnalenotificări asincrone scurte (SIGTERM, SIGKILL...).
    Memorie partajată (shm)cea mai rapidă metodă — procesele scriu/citesc aceeași zonă de RAM.
    Socket-uri Unixcomunicare bidirecțională, local, tip stream sau datagram (folosit intens de systemd, D-Bus).
    Semafoare / mutex-uricoordonează accesul la resurse partajate.
    Message queuesmesaje structurate, cu prioritate, între procese.

    Sincronizare internă în kernel

    Kernel-ul însuși rulează concurent pe mai multe nuclee CPU, deci trebuie să-și protejeze propriile structuri de date:

    • Spinlock — așteaptă activ (busy-wait) într-o buclă scurtă; folosit când secțiunea critică e foarte scurtă și nu se poate dormi (ex: în handler de întrerupere).
    • Mutex — ca un spinlock, dar procesul care așteaptă e adormit (nu consumă CPU) — pentru secțiuni critice mai lungi.
    • RCU (Read-Copy-Update) — permite multor cititori să acceseze o structură fără lock deloc, în timp ce scrierile creează o copie nouă și o "publică" atomic. Esențial pentru performanța pe multe nuclee.

    12Namespaces și cgroups — fundația containerelor

    Docker, Podman și Kubernetes nu folosesc un kernel separat — containerele sunt procese Linux obișnuite, izolate cu două funcționalități din kernel:

    Namespaces — ce vede

    PID (proprii PID-uri), NET (propria stivă de rețea), MNT (propriul arbore de fișiere montate), UTS (hostname), IPC, USER (mapare UID proprie).

    cgroups — cât poate folosi

    Limitează și contorizează CPU, memorie, I/O disc și lățime de bandă de rețea per grup de procese. cgroups v2 unifică ierarhia pentru toate resursele.

    Un singur kernel Linux (host)
    🐳 Container A

    namespace PID/NET/MNT propriu · cgroup: max 1 CPU, 512 MiB RAM

    🐳 Container B

    namespace PID/NET/MNT propriu · cgroup: max 2 CPU, 1 GiB RAM

    🖥️ Proces normal

    vede tot sistemul, fără izolare de namespace

    Toate rulează pe același kernel — izolarea e logică (namespaces), nu virtualizare hardware.

    $ unshare --pid --net --mount --fork bash   # creează manual namespace-uri noi (demonstrativ)
$ systemd-cgtop                              # consum de resurse per cgroup, live
$ cat /sys/fs/cgroup/<grup>/cpu.max          # limita CPU a unui cgroup (v2)
    🧠 Diferența față de mașinile virtuale: o VM virtualizează hardware-ul și rulează un kernel complet separat (mai izolat, mai greu); un container partajează kernel-ul host-ului (mai ușor, pornește instant, dar izolarea e mai "subțire").

    13Module de securitate (LSM)

    Peste modelul clasic user/grup/permisiuni, Linux Security Modules (LSM) adaugă politici suplimentare de control al accesului, verificate la fiecare apel de sistem relevant:

    • SELinux (Red Hat/Fedora/CentOS) — control obligatoriu al accesului (MAC): fiecare proces și fișier are o etichetă; politica decide ce etichetă poate accesa ce etichetă, indiferent de permisiunile Unix clasice.
    • AppArmor (Ubuntu/Debian/SUSE) — similar ca scop, dar profilurile se scriu pe cale de fișier, nu pe etichete — considerat mai simplu de administrat.
    • seccomp — restricționează ce apeluri de sistem poate face un proces (ex: containerele Docker rulează cu un filtru seccomp implicit care blochează sute de syscalls rar folosite/periculoase).
    • Capabilities — vezi secțiunea 4: privilegii root granulare, în loc de tot-sau-nimic.
    $ getenforce                 # modul curent SELinux (Enforcing/Permissive/Disabled)
$ aa-status                  # profiluri AppArmor active
$ docker run --security-opt seccomp=default.json ...   # profil seccomp custom

    14Cum pornește kernel-ul (boot)

    1. Firmware
    BIOS/UEFI: teste POST, alege un dispozitiv boot-abil
    →
    2. Bootloader
    GRUB încarcă imaginea kernel (vmlinuz) + initramfs în RAM
    →
    3. Decompresie kernel
    nucleul se auto-extrage și inițializează structurile interne
    →
    4. Detectare hardware
    drivere, montează rădăcina reală (folosind initramfs ca punte)
    →
    5. PID 1
    kernel-ul lansează init/systemd, primul proces userspace
    • vmlinuz — imaginea kernel-ului comprimată (numele vine de la "vm" = memorie virtuală + "linuz" = Linux gzip-uit).
    • initramfs/initrd — un mic sistem de fișiere temporar, încărcat integral în RAM, cu doar driverele/uneltele minime necesare să găsească și să monteze discul real (util mai ales cu discuri criptate, RAID, LVM).
    • Parametri de kernel la boot — GRUB poate transmite kernel-ului parametri în linia de comandă (ex: quiet splash, root=/dev/sda1, nomodeset); vezi /proc/cmdline pentru cei folosiți la boot-ul curent.
    $ cat /proc/cmdline           # parametrii de boot ai kernel-ului curent
$ dmesg | head -50             # log-ul complet al inițializării kernel-ului

    Pentru pașii dinaintea kernel-ului (BIOS, MBR, GRUB în detaliu) și inițializarea userspace (init/systemd) — vezi capitolul 6 din cursul OS Book.

    15Configurare și compilare

    Kernel-ul e extrem de configurabil: mii de opțiuni decid ce funcționalități sunt compilate built-in, care ca module (=m), și care sunt excluse complet. Configurația trăiește într-un fișier .config, generat interactiv sau din presetări:

    $ make menuconfig     # interfață text interactivă (ncurses) pentru configurare
$ make xconfig         # variantă grafică (Qt)
$ make defconfig       # configurație implicită rezonabilă pentru arhitectura curentă
$ make -j$(nproc)      # compilează kernel-ul folosind toate nucleele disponibile
$ make modules_install install   # instalează modulele + imaginea kernel

    Opțiunile din menuconfig vin din fișiere Kconfig distribuite în tot codul sursă — fiecare driver/subsistem își declară acolo opțiunile și dependențele.

    Valoare în .configÎnseamnă
    CONFIG_X=ycompilat direct în imaginea kernel-ului (built-in)
    CONFIG_X=mcompilat ca modul separat (.ko), încărcabil la nevoie
    CONFIG_X absentfuncționalitatea nu e inclusă deloc
    🛠️ Majoritatea utilizatorilor nu compilează niciodată kernel-ul — distribuțiile livrează un kernel precompilat, cu configurație generică + module pentru aproape orice hardware. Recompilarea manuală e utilă pentru: hardware embedded, optimizare extremă, patch-uri custom sau învățare.

    16Versionare și ciclul de dezvoltare

    Versiunile kernel-ului urmează schema MAJOR.MINOR.PATCH (ex: 6.9.4). Dezvoltarea e coordonată de Linus Torvalds prin git (pe care el însuși l-a creat, în 2005, tot pentru a gestiona dezvoltarea kernel-ului) și mii de contribuitori, coordonați prin liste de discuții (LKML).

    Tip de versiuneCiclu de viațăPentru cine
    Mainlineo versiune nouă la ~9-10 săptămâniultimele funcționalități; dezvoltatori, testeri.
    Stablepatch-uri de bug-fix/securitate pe o versiune mainline, până apare următoareautilizare generală imediat după lansare.
    Longterm (LTS)întreținută 2-6 ani (ex: 6.1, 5.15, 5.10)distribuții enterprise, servere, embedded — stabilitate pe termen lung.

    Un ciclu de dezvoltare mainline are, simplificat, o fereastră de "merge" de ~2 săptămâni (se acceptă funcționalități noi), urmată de 7 candidați de lansare (-rc1...-rc7) în care se rezolvă doar regresii/bug-uri, apoi lansarea finală.

    $ uname -r                     # versiunea kernel-ului rulat curent
$ cat /proc/version              # versiune + compilator + dată build

    17Parametri și tuning în timpul rulării

    Multe comportamente ale kernel-ului pot fi ajustate fără recompilare, prin sysctl (care citește/scrie în /proc/sys):

    $ sysctl -a | less                       # toți parametrii disponibili
$ sysctl vm.swappiness                    # citește un parametru (cât de agresiv se face swap)
$ sudo sysctl -w net.ipv4.ip_forward=1     # setează temporar (până la reboot)

    Kernel panic vs. oops

    • Oops — kernel-ul detectează o eroare internă (ex: acces la memorie invalidă) dar reușește să continue, de obicei terminând procesul vinovat; mesajul apare în dmesg.
    • Panic — o eroare din care kernel-ul nu se mai poate recupera în siguranță (structuri interne corupte); sistemul se oprește complet, afișând ultimul mesaj pe ecran.
    🩺 Un panic la boot e adesea urma unui driver/modul incompatibil sau a unui parametru de boot greșit — parametrul nomodeset sau boot-area cu un kernel LTS anterior sunt primele lucruri de încercat.

    19Subiecte avansate

    Virtualizare — KVM

    KVM (Kernel-based Virtual Machine) transformă kernel-ul Linux însuși într-un hipervizor de tip 1: folosind extensiile de virtualizare ale CPU-ului (Intel VT-x/AMD-V), procesele "invitate" rulează cod aproape nativ. QEMU se ocupă de emularea dispozitivelor virtuale, KVM de execuția CPU/memorie eficientă. Stă la baza majorității cloud-urilor (OpenStack, Proxmox, GCP...).

    Kernel real-time — PREEMPT_RT

    Kernel-ul standard optimizează pentru throughput mediu, nu pentru latență garantată. Patch-ul PREEMPT_RT (parțial integrat deja în mainline) face aproape tot codul kernel-ului întreruptibil, oferind latențe maxime predictibile — esențial pentru robotică, control industrial, audio profesional.

    Power management

    ACPI oferă interfața standard prin care kernel-ul interoghează și controlează starea de energie a hardware-ului (baterie, temperatură, stări de sleep S1-S4). cpufreq ajustează dinamic frecvența CPU (governors: performance, powersave, ondemand, schedutil) pentru echilibrul putere/consum.

    eBPF — programabilitate în kernel

    eBPF permite atașarea de mici programe (verificate static pentru siguranță) direct în puncte din kernel — rețea, syscalls, scheduler — fără a scrie și încărca un modul. Stă la baza uneltelor moderne de observabilitate (bpftrace, Cilium) și securitate (Falco).

    20Glosar rapid

    PIDProcess ID — identificatorul unic al unui proces.
    ABIApplication Binary Interface — contractul stabil de apeluri de sistem între kernel și userspace.
    MMUMemory Management Unit — componenta hardware care traduce adrese virtuale în adrese fizice.
    IRQInterrupt Request — semnal hardware că un dispozitiv are nevoie de atenția CPU.
    LKMLoadable Kernel Module — cod încărcabil/descărcabil dinamic în kernel (.ko).
    LSMLinux Security Module — cadrul pe care se bazează SELinux/AppArmor.
    cgroupControl Group — mecanism de limitare/contorizare a resurselor unui grup de procese.
    namespacemecanism de izolare a vizibilității unei resurse (PID, rețea, montări...) pentru un grup de procese.
    OOM killermecanismul care termină forțat un proces când memoria e complet epuizată.
    LTSLong Term Support — versiune de kernel întreținută mulți ani.
